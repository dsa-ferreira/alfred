# alfred 0.6.0 update

The owner can now switch alfred between several models ("brains") from the
Telegram chat, and alfred says "sir" less often. For the infra side, this
release brings a new image tag, a bigger startup model and a new
`[ai.models]` table in `alfred.toml`. Both models listed there must be
available on `ollama-gpu`. There are no new secrets, dependencies, ports,
volumes or migrations.

## Details

**The `[ai]` section** of the rendered `alfred.toml` now looks like this:

```toml
[ai]
base_url = "http://<ollama-gpu>:11434"
model = "gemma4:26b-a4b-it-qat"   # startup brain, and the fallback
# ... the other [ai] keys, unchanged ...

[ai.models]                       # optional table; alias = "model tag"
gemma = "gemma4:26b-a4b-it-qat"
bonsai = "<the bonsai tag on ollama-gpu>"
```

Aliases must be lowercase letters, digits and hyphens. Each tag must be
non-empty and listed once. A violation stops alfred at startup with an error
naming `ai.models`. If no alias names `[ai] model`, that model is still a
brain, listed under its tag. Without the table, alfred runs on `[ai] model`
alone and offers no switching.

**Switching.** The owner asks in plain words ("set your brain to bonsai"),
and the next message goes to that model. The choice is kept in memory only,
so a container restart puts alfred back on `[ai] model`. Ollama loads the
new model on the next message, which can take as long as a cold start. The
existing 300-second request timeout covers it.

**Fallback.** Suppose a model request on a brain other than `[ai] model`
fails with a 4xx or an unreadable reply. That covers a tag missing on
`ollama-gpu` and a model that can't use tools. alfred then switches back to
`[ai] model`, tells the owner, and logs a WARNING
(`turn <n>: brain bonsai failed (...); back on gemma`). If no tool had run
yet, the message is answered again on `[ai] model`. An unreachable
`ollama-gpu` does not trigger this; it still goes through the normal queue
retry.

**Summaries** now use gemma4:26b-a4b-it-qat as well, because
`memory.summary_model` is unset and so follows `[ai] model`.

**Persona.** The built-in persona addresses the owner (`owner_address`) only
occasionally instead of in nearly every reply. Nothing to configure. The
fixed notices are unchanged and still end with it.
