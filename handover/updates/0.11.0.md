# alfred 0.11.0 update

alfred now serves several people: each configured user chats in their own
private Telegram chat, with their own conversation, memory, attachments and
tool allow-list, and exactly one of them is the admin. For the infra side,
this release brings a new image tag, a **breaking `alfred.toml` change**
(`[[users]]` replaces `[telegram] owner_user_id` and `[ai] owner_address`),
migration `0005` (run on start), which needs `ALFRED_MIGRATE_ADMIN` once,
and optional per-user MCP token variables.

```yaml
handover_update: 1
service: alfred
from: 0.10.0
to: 0.11.0

before:
  - pg_dump the alfred database (0.11.0 adds migration 0005; see rollback)
  - Decide the admin's user name (lowercase letters, digits and hyphens, e.g. diogo). It must be the same in ALFRED_MIGRATE_ADMIN and in the admin's [[users]] name.

changes:
  - change: changed
    path: components.alfred.image
    value: album.lan/alfred:0.11.0  # linux/amd64; see Open questions
  - change: added
    path: components.alfred.env.ALFRED_MIGRATE_ADMIN
    value: {value: TODO}  # the admin's [[users]] name, see `before`
    why: >
      The entrypoint runs `alfred migrate` before serving. Migration 0005
      assigns every existing conversation, message, reminder and attachment
      to this user. Without it (or with a value that isn't a user name) the
      migration refuses, changes nothing, and the container exits. It is read
      only by that migration; it can stay set afterwards, or be removed once
      0005 has run.
  - change: removed
    path: components.alfred.files[/etc/alfred/alfred.toml].telegram.owner_user_id
    data: migrate: becomes users[0].telegram_user_id (the admin)
  - change: removed
    path: components.alfred.files[/etc/alfred/alfred.toml].ai.owner_address
    data: migrate: becomes users[0].address (the admin)
  - change: added
    path: components.alfred.files[/etc/alfred/alfred.toml].users
    value:
      - name: {value: TODO}               # the admin; same as ALFRED_MIGRATE_ADMIN
        telegram_user_id: {value: <today's telegram.owner_user_id>}
        address: {value: <today's ai.owner_address, or "sir">}
        admin: {value: true}
        tools: {value: ["*"]}             # every tool, as today
      - name: {value: TODO}               # the second user
        telegram_user_id: {value: TODO}
        address: {value: TODO}            # e.g. "madam"
        tools: {value: TODO}              # e.g. ["alfred_*", "cookbook_*", "mcparr_find_media", "mcparr_add_media"]
        mcp_tokens: {value: {mcparr: ALFRED_MCP_TOKEN_MCPARR_<USER>}}   # optional, see below
    why: >
      Required, at least one entry, exactly one admin. 0.11.0 rejects the old
      keys as unknown and won't start until the file is rewritten. See
      Details for the rendered block.
  - change: added
    path: secrets.mcparr_token_<user>
    value:
      generate: user_provided  # an mcparr token for the second user; may hold the same value as mcparr_token for now
      used_by: [alfred, mcparr]
      rotation: issue a new token on mcparr, update the secret, restart alfred. Until then her mcparr tools fail and the model tells her so.
    why: >
      Optional. Lets mcparr tell users apart later (who asked for a
      download). Without a user's mcp_tokens entry for a server, that
      server's own token_env is used, as today.
  - change: added
    path: components.alfred.env.ALFRED_MCP_TOKEN_MCPARR_<USER>
    value: {from: secret, name: mcparr_token_<user>}
    why: only if the second user's [[users]] entry names it in mcp_tokens

after: []

verify:
  - "docker exec alfred alembic current  ->  0005 (head)"
  - "docker logs alfred  ->  'alfred started: ... users <admin>, <second user> (admin <admin>)' and no 'invalid configuration' error and no 'is not in [[users]]' warning"
  - "The admin sends 'what did we talk about last?'  ->  answered from the existing history (it was assigned to the admin)"
  - "The second user messages the bot  ->  a reply in her chat only; her context holds none of the admin's messages"
  - "The admin says 'remind <second user> to test alfred in 2 minutes'  ->  two minutes later she gets the reminder, told the admin set it"
  - "curl -X POST /notify with {\"text\": \"hi\", \"user\": \"<second user>\"}  ->  200, she receives '[<service>] hi'; with an unknown user  ->  422"

clients: >
  /notify and /ask accept an optional "user" (a [[users]] name). Without it,
  they go to the admin, so existing callers keep working unchanged. An
  unknown name is refused with 422 and nothing is sent or queued.
rollback: >
  1) Stop alfred. 2) The old schema allows only one current conversation in
  total: if the second user has chatted, end her conversation first
  (UPDATE conversations SET ended_at = now() WHERE user_name = '<second user>'
  AND ended_at IS NULL), otherwise the downgrade fails. Her rows otherwise
  lose their owner and become the admin's. 3) Undo migration 0005 with the
  0.11.0 image:
  docker run --rm -e ALFRED_DATABASE_URL=<same url> album.lan/alfred:0.11.0 alembic downgrade 0004
  4) Restore the 0.10.0 alfred.toml ([telegram] owner_user_id and [ai]
  owner_address instead of [[users]]). 5) Pin album.lan/alfred:0.10.0.
  ALFRED_MIGRATE_ADMIN and per-user MCP token variables can stay set; 0.10.0
  ignores them. Restoring the pre-upgrade dump is the alternative to 2 and 3.
```

## Details

**Migration 0005** runs in the entrypoint's `alfred migrate`, in one
transaction, in well under a second for a single owner's data. It adds a
user name to conversations, queue items and attachments and a creator to
reminders, fills them from `ALFRED_MIGRATE_ADMIN` and makes them required,
adds a `reminder_recipients` table (the admin becomes the recipient of every
existing reminder), renames the stored message kind `owner` to `user`, and
replaces "one current conversation" with "one current conversation per
user". On an empty database the variable isn't needed. No superuser, no
extension.

The migration can't check the name against `alfred.toml`. At startup alfred
logs a warning for any user name in the database that is not a configured
user; those rows are invisible to everyone. If the name was misspelt, fix it
by hand, e.g. `UPDATE conversations SET user_name = 'diogo' WHERE user_name =
'dioog'` (and the same for `queue_items`, `attachments`,
`reminders.created_by`, `reminder_recipients.user_name`).

**The `[[users]]` block** replaces the `[telegram]` section (delete it, or
leave it empty) and `owner_address` under `[ai]`:

```toml
# The admin: today's owner. Default target of /notify and /ask, the only
# one offered brain switching, and told when a brain fails on anyone's turn.
[[users]]
name = "<admin name>"            # = ALFRED_MIGRATE_ADMIN
telegram_user_id = <today's owner_user_id>
address = "<today's owner_address>"   # default "sir"
admin = true
tools = ["*"]                    # every tool, as today

# The second user: her own private chat, conversation and memory.
[[users]]
name = "<her name>"
telegram_user_id = <her Telegram user ID>
address = "madam"
# Exact tool names as the model sees them, prefixes ending in *, or "*".
# Each entry must be *, or start with alfred_ or a configured server's name
# and _; an unknown alfred_ name is a startup error. An empty list offers no tools.
tools = ["alfred_*", "cookbook_*", "mcparr_find_media", "mcparr_add_media"]
# Optional: her own token per MCP server; other servers use their token_env.
mcp_tokens = { mcparr = "ALFRED_MCP_TOKEN_MCPARR_<USER>" }
```

Validation at startup, all reported together: no `[[users]]` entry,
duplicate names or Telegram IDs, zero or several admins, an `mcp_tokens` key
that isn't a configured MCP server, a token variable that is unset or empty,
and the tool rules above. A user's MCP token may hold the same value as
another user's or the server's own.

**What changes for the second user.** Messages from her Telegram ID in her
private chat are answered; group chats and anyone else are still ignored. An
MCP server none of her `tools` entries can match is not contacted on her
turns at all. All users share the one queue, so her message waits while the
admin's turn runs. Reminders can be set across users ("remind ana to buy
milk at six", "remind us ..."): each recipient gets one in their own chat,
and shared reminders cost one model turn per recipient.

No new ports, dependencies, volumes or network connections. Resource use is
unchanged apart from the second user's turns.
