# alfred 0.10.0 update

The owner can now send alfred photos, image files and PDFs and ask about
them. For the infra side, this release brings a new image tag, database
migration `0004` (run automatically on start), a new S3 dependency (a bucket
on the homelab's Garage) with its key as two new secrets, an `[attachments]`
section and vision flags in `alfred.toml`, and a new outbound connection to
Garage's S3 endpoint. Without an `[attachments]` section, 0.10.0 behaves like
0.9.0 (text only) and needs none of the new pieces.

## Details

**Migration 0004** runs in the entrypoint's `alfred migrate`, before the
service starts, like the earlier ones. It only adds two tables:
`attachments` (one row per file: type, size, file name, object key, which
message and conversation entry it belongs to) and `attachment_pages` (each
PDF page's text). No superuser, no extension, well under a second.

**The `[attachments]` section** of the rendered `alfred.toml`:

```toml
[attachments]
# Garage's S3 API endpoint and alfred's bucket (both required).
endpoint_url = "http://<garage host>:<s3 api port>"
bucket = "alfred"
# Region name used to sign requests; must match Garage's s3_region.
region = "garage"
# Largest file accepted, in bytes; at most 20000000 (Telegram's bot limit).
max_bytes = 20000000
# How many of the newest owner messages send their images to the model.
inline_turns = 1
# Characters of a PDF's page 1 text sent with the message that brings it.
first_page_chars = 4000
# Characters of PDF text in one alfred_read_document result.
read_chars = 8000
# Longer side, in pixels, of images sent to the model.
image_max_px = 1536
# Seconds to wait for the rest of a Telegram album.
album_wait_s = 2
```

And the brains, rewritten as tables (keep the bonsai tag that is configured
today):

```toml
[ai.models]
gemma = { model = "gemma4:26b-a4b-it-qat", vision = true }
bonsai = { model = "<the bonsai tag already configured>", vision = true }
```

With `[attachments]` set and either `ALFRED_S3_*` variable missing, alfred
exits at startup with an error naming the variable. `max_bytes` above
20000000 is also a startup error.

**How alfred talks to Garage.** One S3 client for alfred's lifetime, path-style
addressing, request and response checksums only when the operation needs
them (newer AWS-style checksum headers, which Garage may reject, are not
sent), a 10 s connect and 60 s read timeout, and at most 3 attempts per
request. Objects are written under `attachments/<random uuid>`; the key
never contains the file name. Errors are logged with the operation, the key
and the error code only. Nothing reaches the bucket except through alfred.

**When Garage is down.** A file the owner sends is refused with "I couldn't
keep that file. Kindly send it again." and nothing is queued. Earlier
attachments that the model wants to look at again come back as "not
available right now", and the turn still answers. Text messages are not
affected.

**Data and backups.** Files are kept as long as their conversation,
archived ones included; alfred never deletes an attachment. The only
deletions are orphans: a background task, at startup and then every 24 h,
deletes objects under `attachments/` older than a day that no database row
refers to (left by a crash between upload and the database write). Postgres
backups no longer cover everything: back up the bucket too. For a
consistent restore, restore Postgres first, then the bucket; objects with no
row are cleaned up by the orphan task within a day, while a row whose object
is missing shows as "not available right now".

**Resources.** Each owner turn on a vision brain with a new image costs more
prompt tokens on ollama-gpu (an image is at most 1536 px on its longer side,
JPEG quality 85). Only the message that brings a file carries the image;
later turns carry a short handle, so per-turn cost doesn't grow with the
number of files in a conversation. The context log line counts images:
`history <n> entries <chars> chars, 1 image`.

## Open questions

- `album.lan/alfred:0.10.0` is not built yet. Before deploying this update,
  commit the work and the version bump to 0.10.0 and run `make push` from
  this repo.
- Garage's S3 API endpoint (host and port) for `attachments.endpoint_url`,
  reachable from alfred's host.
- Garage's `s3_region`. alfred assumes `garage`, Garage's default; set
  `attachments.region` to the configured value if it differs.
- Is Garage backed up, and how? The bucket now holds data that Postgres
  backups don't cover (`backup: required`).
- Expected bucket growth depends on how much the owner sends; not measured.
- alfred's memory use with attachments is not measured; see the memory entry.
