# alfred 0.17.0 update

Each part of alfred now owns its own database tables, and the ten old
migrations are replaced by one new baseline. For the infra side: a new image
tag, and **the `alfred` database must be dropped and recreated**. Its
conversations, facts, reminders and attachment records are not carried over.
`ALFRED_MIGRATE_ADMIN` is no longer read.

```yaml
handover_update: 1
service: alfred
from: 0.16.2
to: 0.17.0

before:
  - pg_dump the alfred database (custom format, e.g. pg_dump -Fc alfred > alfred-0.16.2.dump); it is the only way back to 0.16.2
  - Stop alfred (docker compose stop alfred)
  - "Drop and recreate the alfred database, owned by alfred: as a superuser, DROP DATABASE alfred; CREATE DATABASE alfred OWNER alfred; then in it CREATE EXTENSION IF NOT EXISTS vector; (or, in the existing database: DROP SCHEMA public CASCADE; CREATE SCHEMA public AUTHORIZATION alfred; CREATE EXTENSION IF NOT EXISTS vector;)"

changes:
  - change: changed
    path: components.alfred.image
    value: album.lan/alfred:0.17.0  # linux/amd64; see Open questions
  - change: removed
    path: components.alfred.env.ALFRED_MIGRATE_ADMIN
    data: discard  # nothing reads it any more; the vault value can be deleted
    why: Only migration 0005 read it, and that migration no longer exists.

after:
  - Start alfred (docker compose up -d alfred). The entrypoint's `alfred migrate` creates every table at revision s001.

verify:
  - "docker exec alfred alembic current  ->  s001 (head)"
  - "docker logs alfred  ->  'alfred started: ...', no migration error"
  - "A user sends the bot a first message, e.g. 'hello'  ->  alfred replies as usual"
  - "A photo or PDF sent to the bot is answered about (if [attachments] is set)"

clients: none
rollback: >
  1) Stop alfred. 2) Drop and recreate the alfred database with the vector
  extension, as in `before`. 3) Restore the dump into it
  (pg_restore -d alfred --no-owner --role=alfred alfred-0.16.2.dump).
  4) Pin album.lan/alfred:0.16.2 and start it.
```

## Details

**Why the wipe.** alfred is still in single-owner use and its owner accepted
losing its data, so the schema was reshaped rather than migrated: each table
now belongs to one part of alfred, and migrations `0001`-`0010` are replaced
by one baseline, `s001`. There is no data migration.

**What is lost.** Every conversation and its history, archived conversations
and their summaries, learned and told facts, reminders (including repeating
ones), pending queue items and open questions, and the attachment records.
Users start with an empty conversation; repeating reminders must be set again.

**An old database is refused.** If the database is not dropped first,
`alfred migrate` sees revision `0010`, stops before changing anything with
"this database was created by alfred 0.16 or older and can't be upgraded; drop
and recreate it (see the 0.17.0 handover update)", and the container exits
with status 1. Nothing in the old database is touched, so rolling back to
0.16.2 without a restore also works in that case.

**Attachment files.** The files in the S3 bucket under `attachments/` lose
their rows with the wipe. alfred's orphan sweeper deletes objects that no row
refers to once they are a day old, so the bucket empties itself in the first
day; nothing to do by hand. After a rollback with a restored dump, the
sweeper may already have deleted them: old attachments then can't be viewed
again.

**Downtime.** alfred is down from the stop in `before` until it is up again
after `after`: a minute or two. Messages sent to the bot meanwhile are
delivered by Telegram once alfred polls again, and land in the new database.

No change to `alfred.toml`, other environment variables, secrets, ports, the
health check, resources or integrations.
