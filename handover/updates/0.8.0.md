# alfred 0.8.0 update

alfred can now remind the owner of things at a given time ("remind me to
call mum at five"). For the infra side, this release brings a new image tag,
database migration `0003` (run automatically on start) and an optional
`[reminders]` section in `alfred.toml`. There are no new secrets,
dependencies, integrations, ports, volumes or outbound connections.

```yaml
handover_update: 1
service: alfred
from: 0.7.0
to: 0.8.0

before:
  - pg_dump the alfred database (0.8.0 adds migration 0003; see rollback)

  - change: changed
    path: components.alfred.image
    value: album.lan/alfred:0.8.0  # linux/amd64; see Open questions
  - change: added
    path: components.alfred.files[/etc/alfred/alfred.toml].reminders
    value:
      default_time: {value: "09:00"}
      check_interval_s: {value: 30}
    why: >
      Optional; the values shown are the defaults and the recommended values.
      Leaving the section out is fine. See Details.
  - change: changed
    path: dependencies.db.size

    why: >
      New table `reminders`, one short row per reminder set. Pending
      reminders now live only in this database, see Open questions about
      its backup level.

  - "docker logs alfred  ->  'alfred started: ... reminders checked every 30s, 2 MCP server(s)' and 'reminder loop started, checking every 30s', and no 'invalid configuration' error"

  migration 0003 (drops the reminders table and the reminder_id columns).
  The downgrade fails while delivered reminders exist in the queue or the
  conversation, so delete those first, in the alfred database:
  DELETE FROM turn_tool_calls WHERE queue_item_id IN (SELECT id FROM queue_items WHERE kind = 'reminder');
  DELETE FROM entries WHERE kind IN ('reminder', 'reminder_reply');

  docker run --rm -e ALFRED_DATABASE_URL=<same url> album.lan/alfred:0.8.0 alembic downgrade 0002

  album.lan/alfred:0.7.0. Restoring the pre-upgrade dump is the alternative
```

## Details

**Migration 0003** runs in the entrypoint's `alfred migrate`, before the
service starts, like the earlier ones. It only adds: a `reminders` table with
a partial index, a nullable `reminder_id` column on `queue_items` and on
`entries`, and wider `kind` check constraints on both. It needs no
superuser and no extension, and takes well under a second on alfred's
table sizes. The service is down only for the usual restart.

**The `[reminders]` section** of the rendered `alfred.toml`:

```toml
[reminders]
# Time used for a reminder on a date with no clock time ("on Friday"), HH:MM.
default_time = "09:00"
# Seconds between checks for due reminders. Delivery is at most this late.
check_interval_s = 30
```

`default_time` must be a 24-hour `HH:MM` (00:00 to 23:59); anything else
stops alfred at startup with an error naming `reminders.default_time`.
`check_interval_s` must be positive. Reminder times are read and shown in
the existing `[ai] timezone` (default `Europe/Lisbon`), so check that it is
the owner's timezone.

**How it runs.** A fifth background task in the same process checks the
database every `check_interval_s` for due reminders and puts them in the
message queue. The check is one indexed query; it makes no AI requests and
opens no new connections. A due reminder becomes one normal AI turn on
`ollama-gpu` (about as heavy as an `/ask`), so it wakes the GPU box only
when a reminder is actually due. If the AI is asleep or unreachable, the
reminder waits and is retried like any queued message. If the turn fails,
alfred sends a fixed reminder message without the AI.

**Downtime.** Reminders are stored in Postgres and survive restarts and
redeploys. One that came due while alfred was down is sent as soon as it
starts again, however late. A long outage is therefore not a lost reminder,
but losing the database is.

**Logging.** Setting, cancelling and queueing a reminder each log one INFO
line with the reminder's number and due time. Reminder texts appear in the
turn log lines like any message. None of it is secret.

## Open questions

- `album.lan/alfred:0.8.0` must be pushed before deploying this update. Run
  `make push` from this repo once the 0.8.0 version bump is committed.
- The handover lists the alfred database's backup as `nice_to_have`. It now
  also holds reminders that haven't fired yet, which nothing else keeps.
  Should the backup level stay `nice_to_have` or become `required`? (Owner's
  decision.)
