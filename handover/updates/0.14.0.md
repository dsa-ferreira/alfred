# alfred 0.14.0 update

Reminders can now repeat ("every weekday at 8, brief me on the weather"),
and a reminder's turn may look things up with the user's tools before it
writes the message. For the infra side: a new image tag and migration `0008`
(runs on start). No new settings, secrets, ports or dependencies. Repeating
briefings mean more turns with tool calls on ollama-gpu and the MCP servers.

## Details

**Migration 0008** adds four columns to `reminders`: `repeat`,
`repeat_days`, `repeat_time` (all nullable) and `quiet_ok` (default false),
with three CHECK constraints. It adds a nullable `reminder_due_at` to
`queue_items` and to `entries`, filled in for existing reminder rows with a
single `UPDATE ... FROM reminders` each. It also allows a new
`conversations.end_reason` value, `unattended`. Even with a long history it
takes a second or two. It runs in the entrypoint's `alfred migrate`, like
the earlier ones. Existing reminders stay one-off and behave as before.

**Repeating reminders** have a daily, weekdays, weekends or weekly rule at
a local `HH:MM` in `ai.timezone`, so they keep their wall-clock time across
DST changes. Changing `ai.timezone` moves every series to the same wall
time in the new zone, starting from its next occurrence after the one
already scheduled. Everything is in Postgres. There is no new timer: the
existing due-reminder loop picks them up, and restarts are safe. After
downtime a repeating reminder is delivered once, for its most recent missed
occurrence, not once for each one missed.

**Quiet reminders** ("tell me only if something is downloading") may end
with nothing sent and nothing recorded. The log shows it at INFO
(`reminder item N (#M): NO_REPLY, <user> not notified`). A reminder turn
that fails still sends the fixed reminder notice, quiet or not.

**Who can cancel.** A user cancelling a reminder someone else set for them
now only removes themselves; the other recipients keep it. The creator
still cancels it for everyone. This is a behaviour change for users, not
for the infra side.

**Unattended conversations.** A daily briefing nobody answers no longer
piles up in one conversation. When the next one arrives, the old
conversation is archived and summarised by the existing sweeper, which is
about one extra summary request per day per briefing user. Fact extraction
skips such conversations without a model request.

No new ports, dependencies, secrets, volumes or network connections.
Memory and CPU use of the container are unchanged.
