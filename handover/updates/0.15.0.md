# alfred 0.15.0 update

Fixes user facts being removed for unrelated facts. Duplicates are now
confirmed by the model instead of by embedding distance alone, a
replacement must quote the fact it replaces, and extraction keeps fewer
low-value facts. For the infra side: a new image tag, migration `0009`
(runs on start), and a changed meaning and default for one `[memory]`
setting. The owner also gets SQL to restore facts the old check removed.

```yaml
handover_update: 1
service: alfred
from: 0.14.0
to: 0.15.0

before:
  - pg_dump the alfred database (0.15.0 adds migration 0009; see rollback)

changes:
  - change: changed
    path: components.alfred.image
    value: album.lan/alfred:0.15.0  # linux/amd64; see Open questions
  - change: changed
    path: components.alfred.files[/etc/alfred/alfred.toml].memory.facts_duplicate_max_distance
    value: {value: 0.2}
    why: >
      Its meaning changed. It used to be the distance under which a fact was
      removed as a duplicate; it is now the distance under which a new fact
      and the user's other facts (up to 5, nearest first) are *checked* by
      the model, which decides. The default moved from 0.1 to 0.2. If
      alfred.toml sets it to 0.1 (as the 0.13.0 update showed it), change it
      to 0.2 or remove the line; 0.1 would leave real duplicates unchecked.
      Still must be between 0 and 1, or alfred stops at startup naming the key.
  - change: changed
    path: integrations.ollama-gpu.detail
    value: >
      Unchanged endpoint and models. New: a duplicate-check request for each
      new fact that has another fact of the same user close by, on the
      summary model, streamed, only while alfred's queue is quiet, cancelled
      when a message arrives. Facts with nothing close need no request.
      Fact extraction requests are unchanged in shape; their prompt is
      stricter.

after:
  - "Owner, optional: review facts the old duplicate check and replacements removed, and restore the wrong ones (SQL in Details)"

verify:
  - "docker exec alfred alembic current  ->  0009 (head)"
  - "docker logs alfred  ->  'alfred started: ...' with no migration error, and no duplicate-check lines yet (existing facts count as checked)"
  - "In Telegram: 'remember that I'm allergic to shellfish' twice, then wait for a quiet minute  ->  the log shows 'fact N duplicate check: 1 compared, 1 duplicate; ...' and /memory lists the fact once"
  - "docker logs alfred | grep 'duplicate check failed'  ->  none, or few (each is a WARNING with its attempt count)"

clients: none
rollback: >
  1) Stop alfred. 2) Undo migration 0009 with the 0.15.0 image (0.14.0's
  entrypoint can't start on a database at a revision it doesn't know):
  docker run --rm -e ALFRED_DATABASE_URL=<same url> album.lan/alfred:0.15.0 alembic downgrade 0008
  This drops the three duplicate-check columns; no fact is deleted, and
  facts removed by the new check stay removed. 3) If alfred.toml sets
  facts_duplicate_max_distance = 0.2, set it back to 0.1 (0.14.0 removes
  everything within that distance). 4) Pin album.lan/alfred:0.14.0.
  Restoring the pre-upgrade dump is the alternative to 2.
```

## Details

**Migration 0009** adds three columns to `facts`:
`duplicate_checked_at` (nullable; `NULL` means the check is pending),
`duplicate_attempts` (default 0) and `duplicate_next_at` (nullable), plus a
partial index of pending facts. It sets `duplicate_checked_at = now()` on
every existing fact, so the upgrade starts no backfill. It takes well under
a second and runs in the entrypoint's `alfred migrate`, like the earlier
ones.

**What changed in the background work.** Embedding a fact no longer removes
anything. A new job, after embedding, takes up to five of the user's facts
within `facts_duplicate_max_distance` and asks the summary model which say
the same thing as the new fact. Only those are removed (a told fact is kept
over a learned one, otherwise the older one); a fact on the same topic, one
that adds detail, or one that contradicts it is kept. The check runs only
while no message, `/ask` or reminder is waiting or running and none has
finished for `memory.summary_quiet_s`, like summaries and extraction. A
failed check logs a WARNING with its attempt count and is retried with the
queue's backoff, never given up; it blocks nothing. `alfred_remember` now
always answers "Saved as fact N" and leaves the duplicate check to this job.

Extraction's `REPLACE` lines must now quote the fact they replace. A quote
that doesn't match the fact with that id means nothing is replaced: the new
fact is added and the refusal is logged at INFO, without either text. The
outcome line gains a count:
`conversation 41 facts: 2 added, 1 replaced, 0 replacements refused; ...`.

**Restoring facts the old check removed.** Removals were always only marked,
so nothing was lost. To review the facts removed as duplicates or replaced,
next to the fact that took their place (read-only):

```sql
SELECT f.id, f.user_name, f.removed_reason, f.removed_at::date, f.text,
       r.id AS by_id, r.text AS by_text
FROM facts f LEFT JOIN facts r ON r.id = f.replaced_by
WHERE f.removed_reason IN ('duplicate', 'replaced')
ORDER BY f.user_name, f.id;
```

To restore chosen ones, putting their ids in the list:

```sql
BEGIN;
UPDATE facts
SET removed_at = NULL, removed_reason = NULL, replaced_by = NULL
WHERE id IN (12, 15)
  AND removed_reason IN ('duplicate', 'replaced')
RETURNING id, user_name, text;
COMMIT;  -- or ROLLBACK if RETURNING shows something unexpected
```

A restored fact keeps the `duplicate_checked_at` the migration gave it, so
it isn't judged again. The fact that replaced it stays active too; remove
that one with `/memory forget <id>` if it is wrong. Users can also clean up
their own low-value facts with `/memory forget`. alfred reads facts on every
turn, so neither needs a restart.

No new ports, dependencies, secrets, volumes or network connections.
Resource use is unchanged apart from the extra ollama-gpu requests above.
